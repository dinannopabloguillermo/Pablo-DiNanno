# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

FlowSync is a practice project for the ai4devs course: a team task-management app. It is a monorepo with two independent apps that are **not** currently wired together (frontend still shows the default Vite/React starter page — no API calls exist yet):

- `backend/` — AdonisJS 7 API (Node, TypeScript, ESM)
- `frontend/` — React 19 + Vite (TypeScript)

There is no root-level build tooling; each app has its own `package.json`, and each must be worked on from within its own directory.

## Commands

### Backend (`cd backend`)

```bash
npm install
cp .env.example .env
node ace generate:key        # populates APP_KEY in .env
node ace migration:run
npm run dev                  # serves on http://localhost:3333 with HMR
npm run build                # node ace build
npm run test                 # node ace test (runs unit + functional suites)
npm run lint                 # eslint .
npm run format                # prettier --write .
npm run typecheck             # tsc --noEmit
```

Run a single test file/suite with ace directly, e.g. `node ace test --files "tests/functional/auth.spec.ts"` or `node ace test unit` / `node ace test functional` (suite names come from `adonisrc.ts`).

Useful ace generators: `node ace make:controller`, `make:model`, `make:migration`, `make:validator`.

### Frontend (`cd frontend`, separate terminal — backend keeps running in the first one)

```bash
npm install
npm run dev       # http://localhost:5173
npm run build     # tsc -b && vite build
npm run lint      # oxlint (NOT eslint)
npm run preview
```

No test runner is configured for the frontend yet.

## Backend architecture

### Generated code — do not hand-edit

- `database/schema.ts` and everything under `backend/.adonisjs/` are **auto-generated** (regenerated by `node ace migration:run` / on build via `indexEntities`/`generateRegistry` hooks in `adonisrc.ts`). Never edit these by hand — change a migration or model and regenerate instead.
- Lucid models extend the generated `*Schema` base classes rather than declaring columns directly, e.g. `app/models/user.ts`'s `User extends compose(UserSchema, withAuthFinder(hash))`. Add model-only behavior (getters, hooks, relations) in the model file; add/rename columns via a migration, which regenerates the schema.
- `#generated/controllers` (from `.adonisjs/server/controllers.ts`) is how routes reference controllers (`controllers.NewAccount`, etc.) instead of importing controller classes directly in `start/routes.ts`.

### Import aliases

The backend uses Node subpath imports (defined in `backend/package.json` under `imports`), not relative paths: `#controllers/*`, `#models/*`, `#validators/*`, `#transformers/*`, `#middleware/*`, `#database/*`, `#config/*`, `#start/*`, `#generated/*`, etc. Always import via these aliases to match existing code.

### Request/response conventions

- Every route lives in `start/routes.ts`, grouped under `/api/v1`, further grouped by `auth` (public: `signup`, `login`) and `account` (protected by `middleware.auth()`: `profile`, `logout`).
- Controllers return `serialize(...)` (see `providers/api_provider.ts`), a custom method attached to `HttpContext` that wraps all responses in `{ data: ... }` and understands Lucid pagination metadata. Use `serialize.withoutWrapping(...)` if a response must skip the `data` wrapper. Don't return raw objects from controllers that hit real routes if the rest of the codebase is using `serialize`.
- Response shaping goes through `BaseTransformer` subclasses in `app/transformers/` (e.g. `UserTransformer.toObject()` picks a fixed field allowlist). Add a transformer when exposing a new model over the API rather than serializing the Lucid model directly.
- Input validation uses VineJS schemas in `app/validators/` (`signupValidator`, `loginValidator`), consumed via `request.validateUsing(...)` in controllers.

### Auth

- `@adonisjs/auth` is configured with two guards (`config/auth.ts`): `api` (default) is a stateless **access-tokens** guard for the API, `web` is a session guard. New protected endpoints should use the `api` guard's `auth` middleware (already the default), matching the `account` route group.
- Access tokens are issued via `User.accessTokens.create(user)` and revoked via `User.accessTokens.delete(user, identifier)` — see `access_tokens_controller.ts`.

### Database

- SQLite via `better-sqlite3` (file at `tmp/db.sqlite3`), configured in `config/database.ts`. Commented-out blocks show how to switch to Postgres/MySQL/MSSQL/libSQL if ever needed — swap the `connection` value and install the driver package.
- Migrations live in `database/migrations/`; run `node ace migration:run` after adding one, which also regenerates `database/schema.ts`.

### CORS

`config/cors.ts` allows every origin in dev (`app.inDev`) and nothing in production by default — production origins must be set explicitly (see the commented `CORS_ORIGIN` hint in `.env.example`) before deploying.

## Frontend architecture

The frontend is still the unmodified Vite React-TS template (`src/App.tsx`, `src/main.tsx`) — no routing, state management, or API client has been introduced yet. When building real features here, this is a blank slate: there's no existing pattern to match beyond standard Vite conventions. Note lint uses **oxlint**, not ESLint (`.oxlintrc.json`).
